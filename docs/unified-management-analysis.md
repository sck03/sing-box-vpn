> 本文保留实施前的分析基线。后续代码改动、实际验收与未完成范围见 [统一管理实施记录](unified-management-status.md)。

**本报告编写于实施前，当时仅形成分析，未修改程序。文中“建议”“目标”“验收”均描述当时的后续工作；当前 v4 实现与验收结果以统一管理实施记录为准。**

用户目标：排查 BUG，优化性能、资源占用和稳定性，精简重复代码，提高模块化、解耦性和可扩展性；将原 sing-box 菜单、订阅管理和独立账户管理统一起来。面向新部署，不承担旧版本数据或接口兼容。

## 1. 核心判断与对前述分析的修正

目前的 Web 页面是订阅管理入口，**尚未完整集成原 sing-box 和 VPNGate 菜单**。已有订阅令牌能分别设置下载到期时间与下载次数，但没有形成“每个代理账户独立计费、独立停用”的完整系统。不同下载令牌若返回相同节点凭据，用户实际使用的是同一代理身份。

s-ui、2s-ui 应作为完整 sing-box 管理平台参考，范围包含入站、出站、路由、DNS、TLS、账户、运行状态、管理安全和维护，不能只摘取流量统计功能。

建议继续建设本项目的统一平台，保留已经投入验证的 VPNGate 隔离和订阅编译能力。日常功能集中在一个 Web 面板；订阅转换、账户和用户用量页面属于同一产品。CLI 缩减为引导、恢复、诊断和必要的自动化接口，调用同一业务服务。

本报告纠正以下容易混淆的结论：

| 事项 | 修正后的判断 |
| --- | --- |
| 当前 Web 已覆盖菜单 | 尚未覆盖；详细映射见第 4 节 |
| “独立分享”就是“独立代理账户” | 不是；下载授权和实际代理身份需要分别建模 |
| 订阅模板中的路由就是服务端路由 | 两者作用位置不同，必须分开配置和校验 |
| 官方 sing-box 没有相关 API | 1.14 已有 API 服务，可获取带用户标识的连接与流量事件 |
| 有统计 API 就能可靠限额 | 还需验证断连恢复、持久账本、用户更新和协议会话终止 |
| 参考面板停用用户不会影响其他人 | 取决于协议与实现；2s-ui 部分会话需重建入口 |
| 不兼容旧版就不用管理版本 | 可删除旧兼容路径，但仍需固定核心能力、运行协议和新系统的数据版本 |

### 3.3 不能直接照搬的边界

**协议会话差异。** 2s-ui 的 `DisconnectUser` 明确区分路由连接、可关闭会话和不可直接关闭的入口。对其实现中的 Hysteria/Hysteria2/TUIC，会话移除可能要求重建入口，影响同入口其他用户。其用户更新代码也注明：按用户名保留连接时，只改 UUID 或密码不会立即清除旧认证会话。应借鉴它公开能力限制的做法，并以本项目五协议实测决定支持范围。

**轮询限额不是零超额硬限制。** 两个项目都能看到 10 秒统计和 1 分钟额度检查的安排。正常情况下也存在统计、调度、应用延迟；阻塞时不能保证固定上界。不得把这样的机制描述成“达到额度的瞬间完全停止”。

**WebSocket 不是无成本。** 2s-ui 的配置变化推送仍可能携带完整管理数据。本项目更适合拆分配置摘要、实时状态和秘密查询，使用受限队列与增量事件；已经建立的连接也必须处理会话撤销，不能只在握手时鉴权。

**后台任务按需求启用。** 集群探测、IP 扫描、机器人、邮件、定时备份都增加状态与资源成本。采用它们的生命周期和失败隔离思路，不以功能数量作为第一阶段完成标准。

**许可证。** s-ui 与 2s-ui 均标示 GPL-3.0。若复制、修改并分发其代码或前端资源，应核对对应源码、依赖及分发义务，保留声明并按许可证提供所需材料。当前仅作源码研究；参考行为设计与直接合入代码应分别记录来源。

## 4. 原菜单如何完整整合到统一面板

下面列出可执行的功能去向，避免“增加新页面却丢失原菜单能力”。

| 原功能 | 当前 Web 覆盖 | 统一后的页面或模块 | 整合要求 |
| --- | --- | --- | --- |
| 普通五协议节点 | 未覆盖完整编辑 | 入站与账户 | 首期完整保留 VLESS Reality、VMess WS、Hysteria2、TUIC、AnyTLS |
| UUID、密码设置与随机重置 | 未覆盖 | 账户 → 凭据 | 多账户不再直接共用入口上的单份凭据；支持指定账户与批量操作 |
| 主端口、Hy2 跳跃、TUIC 复用端口 | 未覆盖 | 入站 → 监听与端口 | 共用端口预留、防火墙计划和事务；保留指定 TUIC 端口分享能力 |
| Reality SNI、TLS 参数 | 未覆盖 | 入站 → TLS/Reality | 复用 TLS 资产；Reality 密钥作为入口资产，用户 UUID 独立 |
| VMess WS 路径、Host、CDN 地址 | 未覆盖 | 入站 → 传输与发布地址 | 区分连接地址、TLS SNI、WS Host 和路径 |
| Argo 隧道 | 未覆盖 | 隧道与外部接入 | 可查看状态、参数、日志、启动和停止，并展示依赖 |
| WARP endpoint、本机 SOCKS5 | 未覆盖完整管理 | 出站与端点 | 使用统一对象引用，避免各菜单保存独立副本 |
| 域名走 SOCKS5/WARP、IPv4/IPv6 优先 | 未覆盖服务端管理 | 服务端路由与 DNS | 与客户端订阅模板分开；面板明确显示作用于服务端还是客户端 |
| 导入 PEM、Certbot 申请 | 未覆盖 | 证书 | 支持导入、申请、续期状态、引用入口和变更验证 |
| 修改 VPS IP/域名 | 未覆盖 | 发布地址 | 只更新受影响输出；不应受无关远端订阅故障阻塞 |
| 普通/VPNGate 链接与客户端导出 | 已有订阅相关能力 | 订阅 → 输出与分享 | 所有下载、导出、二维码、分发共用编译器及授权模型 |
| 来源、集合、模板、规则资源 | 已有，但偏配置编辑 | 订阅 → 可视化配置 | 表单和高级 JSON 共用 schema；保留预览、诊断、能力检查 |
| 独立链接、撤销、到期、下载次数 | 已有 | 订阅 → 下载授权 | 补充关联账户与使用权益，明确“下载次数”不是代理流量 |
| 实际代理流量、账户到期、停用 | 缺失完整闭环 | 账户与用量 | 新增独立计量、执行、持久化与恢复 |
| 检测节点、刷新、分发 | 已有部分 | 任务与诊断 | 长操作显示进度、结果、取消状态及失败原因 |
| Telegram、GitLab、WebDAV、PUT、Gist | 分散在菜单与订阅模块 | 通知与分发 | 统一目的地配置、秘密管理及失败重试，避免重复实现 |
| 加密备份、恢复、回收站 | 已有订阅相关能力 | 维护 → 备份恢复 | 扩展为配置、账户、凭据、账本和运行版本一致的恢复方案 |
| 启停、重启、状态、日志 | 未覆盖完整系统服务 | 运行概览与维护 | 区分普通核心、VPNGate 核心、网关、订阅、隧道各自状态 |
| 核心更新、指定版本、回滚 | 未覆盖 | 维护 → 核心与运行环境 | 能力预检、受影响配置验证、保留服务原状态 |
| 程序升级 | 未覆盖 | 维护 → 程序更新 | 与首次安装分离；显示版本、校验、重启与回滚结果 |
| BBR/FQ | 未覆盖 | 维护 → 高级网络设置 | 显示能力、当前值、差异和恢复方式；不宣传普遍提升性能 |
| VPNGate 国家选择、候选节点 | 未覆盖 | VPNGate | 保留出口验证信息与候选状态，不能只展示连接成功 |
| 换 IP、sticky/fixed、暂停/恢复 | 未覆盖 | VPNGate → 运行策略 | 沿用现有网关控制与生命周期，普通节点不受无关操作影响 |
| VPNGate 来源、ISP/hosting 筛选 | 未覆盖 | VPNGate → 来源与策略 | 保留未知信息的明确处理；“家宽候选”不升级为保证住宅出口 |
| VPNGate 独立端口、证书、凭据 | 未覆盖 | VPNGate 的入站/账户视图 | 与普通节点共用编辑组件和业务服务，保持运行隔离 |
| 安装、卸载、首次启用 VPNGate | CLI 为主 | 引导与维护 | 首次安装和失联恢复保留 CLI；Web 展示组件安装状态及授权动作 |

完成统一后，日常导航建议为：**概览、入站、账户、订阅、路由与 DNS、出站与隧道、VPNGate、证书、维护**。Endpoints/Services 等高级对象可放在相应页面中，不必照抄参考面板的全部顶层菜单。

CLI 可以继续提供脚本化管理命令，但不再维护一套独立表单校验、数据模型和发布逻辑。其交互菜单只保留打开面板、安装、重置管理员、服务诊断、配置恢复、升级救援和卸载等常用维护入口。

管理员和订阅用户权限不同。用户自助页只显示自己的权益、用量和订阅；同一个应用可以有隔离的管理与下载监听端口，这属于安全边界，不是增加第二套产品。

### 4.1 超出原菜单、需要补齐的完整核心管理能力

完整整合不能只把终端按钮搬到网页。参考 s-ui/2s-ui 后，以下能力应进入统一平台设计：

| 对象 | 面板应能完成的操作 | 一致性要求 |
| --- | --- | --- |
| 入站 | 创建、编辑、复制、启停、删除、批量绑定账户；常用五协议提供预设 | 监听端口、证书、传输与认证分开；删除入口前展示关联账户和订阅影响 |
| 出站与出站组 | 直连、代理出站、selector/urltest 组、链式引用、手动选择和按需探测 | 校验引用、循环依赖、目标核心能力和探测预算；不可修改受保护的 VPNGate 退路约束 |
| 服务端路由 | 有序规则、规则集资源、域名/IP/协议/入口等条件、最终路由及差异预览 | 前端排序与真实执行顺序一致；账户策略、用户规则和网关保护规则有明确边界 |
| DNS | DNS 服务器、解析策略、规则、缓存及核心支持的高级选项 | 检查 DNS 与出站依赖和解析循环；客户端 DNS 模板另行编辑 |
| TLS/Reality | 证书资产、私钥、到期、续期、使用入口、Reality 参数 | 验证证书/私钥匹配与引用；失败不得替换当前可用材料 |
| Endpoints/Services | 根据固定核心能力管理所支持的端点与服务，并显示状态 | 不因上游支持就默认暴露全部选项；端口、权限和系统资源仍由统一控制层管理 |
| 基础与高级配置 | 日志、缓存、运行参数、配置预览/校验/导出，必要的高级 JSON 编辑 | 高级编辑也经过 schema、引用和权限检查；不能覆盖受管账户表或绕过 VPNGate 保护 |
| 运行诊断 | 实际生效版本、连接/入口/出口流量、失败原因、日志、服务恢复状态 | 明确区分“保存成功”“应用成功”“核心运行”“目标可达”，不以单个绿色状态代替所有检查 |

新增协议或高级对象先登记能力并通过真实核心验证，再显示为可用。完整 sing-box 配置导入需要列出可管理、需确认和不支持的字段；禁止静默丢弃字段或在下一次保存时覆盖高级设置。

界面使用共享表单组件、搜索与分页、批量操作、依赖检查和未保存草稿提示。长任务独立显示结果，常规页面查询不等待核心探测或远端下载。原五协议和 VPNGate 提供简明默认视图，高级资源编辑按需展开。

## 5. 独立到期与流量限制的正确模型

### 5.1 分清不同对象

| 对象 | 保存什么 | 不应承担什么 |
| --- | --- | --- |
| Administrator | 管理员身份、权限、会话、MFA | 不作为代理使用流量的账户 |
| Subscriber | 用户身份、备注、分组、全局禁用状态 | 不与可变名称或 URL token 混作唯一标识 |
| Entitlement | 使用权限：允许入口、到期、配额池、开始与重置策略 | 不直接充当下载令牌 |
| Credential | 某权益在某协议/入口上的认证材料、稳定 ID、代次 | 不与多个需要独立计费的权益共用同一认证身份 |
| SubscriptionGrant | 下载 token 的 hash、允许输出、下载到期、下载次数、撤销状态 | 不承担代理流量计量 |
| UsageLedger | 已结算用量、采集游标、周期与运行代次 | 不跟随重新生成订阅或重启核心归零 |
| Inbound/Route/TLSAsset | 监听、传输、路由和证书资源 | 不再绑定唯一用户的全部状态 |

先实现一个订阅者默认一个权益；模型预留多个权益，是为了让同一个人拥有真正独立的套餐或链接，不要求第一阶段做复杂套餐系统。

### 5.2 用户看到的行为

例如：

| 链接 | 使用权益 | 到期与配额 | 实际关系 |
| --- | --- | --- | --- |
| A 的 sing-box 链接 | A-个人 | 2026-12-01 到期，100 GiB | 与下一行共用 A 的凭据和额度 |
| A 的 Mihomo 链接 | A-个人 | 同上 | 换客户端格式不会获得额外额度 |
| B 的链接 | B-临时 | 2026-11-20 到期，10 GiB | 使用 B 的独立凭据，耗尽只影响 B |
| A 的第二份独立链接 | A-测试 | 24 小时，2 GiB | 新建独立权益和凭据后才具有独立配额 |

“生成独立链接”可以在面板中提供两种清晰操作：“为已有账户增加下载入口”和“创建独立额度的使用账户”。不能仅换 token，却向用户承诺额度独立。

链接自己的下载有效期与账户代理使用有效期允许不同。链接过期只禁止再次获取配置；只有账户到期或禁用并在核心执行，才能阻止已下载配置继续使用。

### 5.3 建议首期支持的策略

- 绝对到期时间；或从创建/首次成功代理认证开始计算时长。首次下载不默认等于首次使用。
- 上行加下行总量配额，按字节存储，界面明确 GiB/GB 单位。
- 总额不重置、每 N 天重置、按指定时区的每月日期重置；处理短月、闰年和夏令时。
- 状态分为正常、未开始、到期、配额耗尽、管理员禁用；到期与手动禁用不能被周期重置意外解除。
- 多客户端格式共用一个权益；普通和 VPNGate 可以共用配额池，也可以明确设为独立池。
- 下载 token 独立轮换/撤销；代理凭据轮换单独执行，并可要求立即关闭旧凭据会话。
- 不限额建议在新模型中使用显式空值，避免把 0 同时解释成“不限”和“已无额度”。

带宽限制、并发连接限制、在线 IP 限制应独立命名和配置。IP 数量不是设备数量；NAT、多地址和移动网络切换都会影响判断。经 CDN/代理接入时也不能不加区分地把对端地址当作真实用户 IP。

### 5.4 必须说明的范围限制

**自建普通节点：** 可在认证入口识别独立用户后统计、禁用。

**VPNGate 节点：** 目前用户流量进入按国家组织的 SOCKS/网关后，原始用户身份会合并。计量必须放在合并之前的已认证 sing-box 入口，不能用国家隧道总量倒推出用户用量。后端转发不再重复计费，保留现有国家验证、断路保护和不回退普通出口的约束。

**第三方订阅节点：** 如果客户端直接连接第三方节点，本项目只能控制下载，无法独立限制该节点上的代理流量。只有第三方支持独立账户与管理接口，或流量实际经过本项目控制的认证入口，才可能执行额度。界面必须显示“本机可执行”或“仅可展示上游信息”。

## 6. 核心能力与运行方式选型

### 6.1 官方 API 已经具备什么

已核对 sing-box v1.14.4 的 API 服务和 StartedService 定义：

- 可订阅运行状态、日志、连接事件及流量。
- Connection 含 `user`、`inbound`、上下行累计与连接标识。
- 可按连接 ID 关闭连接，并控制部分出站选择。
- 重连时有连接状态快照，但这不是已经证明具有持久账本语义的消费日志。
- 所查 StartedService 接口中没有独立的用户增删改 RPC；附着到现有核心的服务与独立托管核心生命周期也不能混为一谈。

因此，官方 API 可以作为观测与控制的第一候选；不能据“无 with_v2ray_api 标签”判定毫无实现可能，也不能据“有 user 字段”判定完整限额已经解决。

### 6.2 后续先完成一个有明确通过条件的能力验证

对五种现有协议分别验证：

1. 同一入口两个用户能否稳定区分，名称变化是否不影响账本身份。
2. TCP、UDP、短连接和多路复用的最终字节数是否完整。
3. 采集器断线、重连、慢消费及核心重启后，遗漏和重复如何识别。
4. 新增、禁用和轮换一个用户需要什么操作，会影响哪些其他连接。
5. 禁用后旧认证会话是否仍能建立新流；仅关路由连接是否足够。
6. 浏览器关闭、订阅服务关闭、管理服务故障时，到期与额度是否仍能执行。
7. API 实际可用性、内存和吞吐影响是否满足部署目标。

这个验证是选型步骤，不是在当前分析轮编写实现。结果形成协议能力表；缺少证据的功能不能在界面标成支持。

### 6.3 推荐的决策顺序

| 路线 | 适用条件 | 成本与限制 |
| --- | --- | --- |
| 外部官方核心 + API 适配器 | 实测能达到所需计量与停用标准 | 上游维护成本较小；可能只能做到重启入口/实例，或无法满足可靠统计恢复 |
| 独立受管核心进程 + 最小必要适配 | 官方接口不能满足独立用户生命周期或限额 | 可接入统计、认证和协议会话；需要维护核心版本及少量适配代码 |
| 在 Web 进程里直接嵌入完整核心 | 更重视部署简单且接受故障耦合 | 与参考项目接近，但面板崩溃/重启可能影响代理，和本项目稳定性目标不完全一致 |
| 直接全面改造成 s-ui/2s-ui 分支 | 接受重做现有特有能力并长期追踪上游 | 需重新适配 VPNGate、事务恢复、严格订阅编译，短期不建议 |
| 同时安装两个面板管理同一核心 | 不建议 | 配置、凭据、端口、更新和恢复会形成多个控制者 |

**建议以外部核心能力验证为第一步；若无法达到标准，采用与 Web 分离的受管运行时。** 不在报告阶段假定某条路线已验证成功。

不论选择哪条路线，都保留普通与 VPNGate 的现有运行隔离。管理页面崩溃不应直接结束代理转发。账户到期及配额执行应靠近运行时，不能依附浏览器，也不能依附是否启用订阅下载。

若采用定制受管运行时，现有“任选最新官方核心替换”的流程必须调整为“安装经过协议与计量验收的运行时版本”；面板显示核心版本、适配版本和能力，不能替换后默默失去限额。

## 7. 统一后的模块和数据边界

### 7.1 保留可复用底座，按职责拆分管理层

| 模块 | 主要职责 | 边界 |
| --- | --- | --- |
| domain | 入口、路由、账户、权益、凭据、证书等类型与规则 | 不依赖 HTTP、CLI、SQLite、systemd |
| application | 命令/查询、权限、revision、任务与应用流程 | Web 和 CLI 共用；不拼接 CLI argv 来调用业务 |
| subscription | 来源解析、集合处理、能力校验、客户端渲染 | 保留当前纯处理模块；不直接控制服务 |
| runtime | 核心适配、账户应用、会话关闭、用量与能力 | 明确普通/VPNGate 实例；可替换具体实现 |
| accounting | 汇总、账本、周期、到期与额度执行状态 | 不与订阅下载计数或图表采样混合 |
| gateway | VPNGate 候选、隔离、验证、隧道生命周期 | 继续复用现有实现，作为领域服务接入 |
| infrastructure | SQLite、文件发布、命令执行、systemd、防火墙、网络获取 | 业务代码通过窄接口使用 |
| transport | HTTP、CLI、状态推送 | 解析输入、认证、调用 application、格式化输出 |
| web | 页面、表单、草稿、图表、任务结果 | 不复制服务端规则，不接触系统命令 |

不必为每个模块启动独立服务。一个程序可以提供管理、受管运行时、网关等少量运行模式；模块分层不等于引入微服务。

~~~mermaid
flowchart TD
    Web[统一 Web 与受限用户页] --> App[应用服务：命令、查询、权限、任务]
    CLI[维护 CLI] --> App
    App --> Model[统一类型模型]
    App --> Store[权威配置与账户账本]
    App --> Compiler[订阅编译器与授权]
    App --> Controller[运行控制与能力适配]
    Controller --> Normal[普通 sing-box 实例]
    Controller --> VPN[VPNGate sing-box 实例]
    VPN --> Gateway[现有 VPNGate 网关与出口验证]
    Normal --> Usage[运行时计量与停用]
    VPN --> Usage
    Usage --> Store
    Compiler --> Snapshots[受限缓存与发布产物]
~~~

### 7.2 数据存储建议

新增持续账户账本后，SQLite 适合作为单机权威状态库，不需要额外数据库服务器。入口、账户、凭据引用、订阅配置、管理员、revision 和应用任务统一保存；运行配置、客户端导出、远端缓存是派生产物。

不能同时让旧 `app.json`、新数据库和面板 JSON 都可独立修改同一配置。面向新部署可以直接采用一个新 schema，旧管理格式不再作为第二条写路径；必要的导入/导出只通过应用服务。

远端资源正文、大型导出、证书文件和历史日志可继续以受限文件保存。SQLite 保存摘要、引用和状态；密钥、代理凭据限制读取权限，备份加密。用于重新生成订阅的代理秘密不能简单只存 hash；管理员密码与下载 token 则应使用合适的散列方案。

数据库事务不能把 systemd、文件替换和运行时应用一起变成原子事务。建议将流程明确为：

1. 读取带 revision 的状态，在锁外完成规划、构建和可行性验证。
2. 提交前复核 revision、核心身份、外部依赖摘要，写入期望配置和待应用记录。
3. 通过现有受控发布机制生成产物、应用受影响运行实例。
4. 健康确认后记录 applied revision；失败记录可恢复状态，页面同时显示期望与实际版本。
5. 重启后根据待应用记录做幂等恢复，避免文件已更新而数据库仍显示旧状态。

普通参数修改失败可保留旧的可用运行配置。账户撤销、到期或额度耗尽属于不同语义：失败时不能恢复旧的有效用户列表并宣称停用成功，必要时关闭受影响入口并明确告警。

### 7.3 面向后续扩展的最小接口

预留 `RuntimeID`、稳定资源 ID、协议能力、用量采集与应用版本即可。新增协议走能力登记与适配器；新增客户端走 subscription renderer；新增通知渠道走事件订阅；新增节点走 runtime 控制接口。

不引入通用脚本插件执行器、任意 shell 面板或多租户计费系统来“预留未来”。这些会增加安全与维护负担。

## 8. 可靠计量、限额与恢复

### 8.1 计数方式

以认证后的稳定账户/权益身份归属流量，入口与出口统计用于诊断，不能再次计入同一用户账本。采用清晰的代理读写字节口径，明确是否含协议开销；不直接用网卡总字节代替用户流量。

实时计数在内存聚合，按批结算。报送包含实例、运行代次、权益/凭据代次和单调游标；数据库在同一事务中更新消费进度与累计量，重放不重复计费。读取后清零的统计 API 必须有单一消费者和失败保留机制，不能由图表页面再次读取并清空。

仅将失败批次留在内存，仍会在进程崩溃时丢失。应有有界本地未确认记录或等价恢复机制，并明确检查点间隔带来的断电损失范围。若要求断电也零漏记或严格零超额，还需要持久额度预留等更强机制，必须测量其开销，不能默认承诺。

### 8.2 额度执行

周期检查方案的超额量约受以下因素影响：

**超额量 ≈ 实际速率 ×（统计延迟 + 检查延迟 + 应用延迟）+ 在途缓冲。**

例如仅 60 秒延迟，在持续 100 Mb/s 下就可能多通过约 750 MB；这只是量级说明，不是本项目实测。当没有速率上限、调度阻塞或执行失败时，也不能把它当成硬上界。

建议把额度判定尽量放在运行时，控制新认证、正在传输的连接及已有协议会话；按明确的数据块或 UDP 包粒度执行。若首期只能提供周期停用，界面与文档必须说明实际延迟和协议影响。

管理进程暂时不可用时，运行时仍按最近确认的有效期和剩余额度工作；过期或耗尽后拒绝新流量。未能恢复必要计量状态时使用明确的受限策略，不能无限放行，也不应无差别关闭所有正常账户。

### 8.3 不可忽略的状态变化

| 场景 | 必须满足的行为 |
| --- | --- |
| 核心重启 | 新运行代次不清空历史累计，也不重复计入旧代次 |
| 管理器重启 | 处理未确认批次，恢复到期定时与应用状态 |
| 更换账户名称 | 账本身份不变 |
| 凭据轮换 | 旧代次不再认证；要求立即失效时关闭旧会话 |
| 配额重置 | 结清旧周期；并发上报不串入新周期 |
| 月末与时区变更 | 重置边界确定、只执行一次，界面显示下一次时间 |
| 下载服务停用 | 代理计量和停用继续运行 |
| 恢复旧备份 | 不静默降低已使用量或复活已撤销账户；区分同机恢复和灾难重建的对账流程 |
| 多实例共享权益 | 汇总普通/VPNGate 使用量；限额执行不能各自完整发放同一份剩余额度 |
| 未来多节点 | 需要额度分配、断网策略和去重结算，单纯每分钟汇总不构成严格全局限额 |

## 9. 本项目已发现问题与修复优先级

P1：影响配置可用性、授权边界或明显资源风险，建议在扩大面板能力前修复。P2：正确性、可观测性或特定路径覆盖问题。优先级针对触发后的影响，并不表示存在未认证远程攻击。

| 编号 | 优先级 | 触发与影响 | 建议修正与验收 |
| --- | --- | --- | --- |
| F1 | P1 | 集合允许重复、大量引用来源；构建先展开节点，再在 Process 检查上限，产生检查前的内存放大 | 限制引用数量并拒绝重复；追加前检查节点预算，预算覆盖中间集合及合计产物；用大量重复引用验证分配受限 |
| F2 | P1 | 本地凭据、端口等修改调用完整订阅 Build；过期的必需远端来源可阻止本地配置维护 | 根据依赖只构建受影响产物；本地运行变更与无关远端资源健康解耦；远端失效时本地变更仍可完成 |
| F3 | P1 | “程序升级”重新走安装流程，执行 enable/restart；用户主动停止的核心或 VPNGate 可能被启动 | 区分首次安装/升级，保存 enabled 与 active 状态；停止态升级后仍保持停止，失败回滚状态可核对 |

## 10. 性能、资源与代码精简的重点

### 10.1 优先优化阻塞与放大，而非先改几行循环

| 优化点 | 当前风险或成本 | 建议 |
| --- | --- | --- |
| 配置全局锁 | 构建、校验或文件工作拉长锁占用，影响并发下载与操作 | 读取快照后锁外规划/验证，提交时复核 revision；保持必要的跨进程操作串行性 |
| 下载次数账本 | 精确次数写入与配置操作争用 | 单独的原子预留/账本事务；不能改成随意批量写而让并发超发 |
| 远端资源任务 | 来源获取已有有界 worker，但资源刷新仍有串行路径，刷新与分发共享调度时序 | 任务分类、有界并发、整轮期限、退避和抖动，长分发不拖延刷新 |
| 预览响应 | 全量产物以 Base64 JSON 传输后前端再删内容，增加网络和内存副本 | 默认返回摘要、诊断、大小、差异；完整正文按需单独下载 |
| 集合处理 | 重复引用、无去重需求仍计算身份、重复规则切片复制 | 在入口限制数量；只计算实际需要的值；一次预算与分配 |
| 正则 | 固定规则重复编译；用户规则重复预处理 | 固定正则预编译，动态规则按配置 revision 编译并限制缓存 |
| 多账户输出 | 账户数 × 格式数 × 模板数导致缓存膨胀 | 共享不含秘密的结构，按账户/凭据代次进行有界产物缓存，限制总字节并失效淘汰 |
| 状态图表 | 高频全量轮询、无人观看仍取系统指标 | 按需订阅、共享采样、页面隐藏降频/取消，历史按时间桶聚合 |
| 日志与任务 | 无上限历史和失败重试放大磁盘/内存 | 明确保留期限、容量、任务结果数量及退避；敏感字段脱敏 |
| 管理模型 | ManagedNode、Profile 与动态 Object 边界来回转换 | 新领域模型为主，旧内部过渡结构逐步移除，动态协议对象局限在核心适配边界 |

账户专用产物的缓存键至少包括权益/权限版本、凭据代次、节点/模板版本和客户端格式，不能只按 output ID 缓存，否则可能向不同账户发送同一凭据。下载鉴权和账户状态检查应早于 304 判断；正文未变也可以返回最新用量元数据。

每个账户不应启动一个 sing-box 进程、一个监听端口或一个常驻定时 goroutine。优先使用支持多用户的共享入口和集中调度；个别协议无法满足隔离条件时明确限制或说明资源代价。

### 10.2 目前性能数据能说明什么

前续本机七节点渲染采样约为：

| 动作 | 时间 | 分配字节 | 分配次数 |
| --- | --- | --- | --- |
| sing-box 渲染 | 61 μs | 24,333 B | 339 |
| Mihomo 渲染 | 56 μs | 20,095 B | 323 |

这是 Windows i5-9400F 的配置生成微基准。项目历史文档中另有不同运行时刻的数值，不能将采样波动当成这份报告带来的优化收益。它们不代表代理吞吐、整机 RSS、Web 流畅度或多人在线性能。

下一阶段应测量配置操作 p50/p95、锁等待、峰值分配、空闲与负载 RSS、goroutine/FD、统计落盘 IOPS、Web 首屏与列表交互，以及启用计量前后的 TCP/UDP 吞吐和延迟。先记录可重复基线，再约定资源上限；不在没有测量时承诺性能提升百分比。

### 10.3 精简代码的取舍

可以删除旧 schema 兼容、重复 shell 表单业务、HTTP 到 CLI 的中转胶水、重复客户端转换器和多个配置真源。应保留资源上限、取消传播、所有权校验、发布恢复、协议能力拒绝和安全失败处理。

“更少代码”不是去掉必要的异常路径。模块以清晰职责和可替换边界划分，避免大量空接口、万能管理器和逐字段搬运的重复层。

## 11. 完整 Web 管理所需的安全与维护设计

当前回环 Web 的 bearer token 和跨源检查是针对本机按需工具的设计，不能直接把监听地址改成公网就视为完整部署方案。

新面板需要：

- 管理员密码散列、持久登录限速、可选 TOTP、服务器端可撤销会话；HTTP 与已连接状态推送都处理撤销。
- 管理员、操作员、只读角色的最小权限；每个 API 在服务端检查对象与操作权限。
- TLS、受控反向代理信任、HttpOnly/Secure/SameSite cookie、CSRF 防护、合理 CSP；秘密查询独立授权并审计。
- 订阅 token、代理凭据、上游密码和私钥不写入访问日志或默认列表响应；用户自助页不包含管理配置。
- 系统操作只接收类型化参数，经现有命令执行层调用固定程序，不接收网页传来的任意 shell。
- 证书续期、核心升级、应用配置等长任务有 ID、阶段、期限和结果；断开网页不应令已开始的一致性提交中断。
- 使用持久任务记录和提交后事件，避免事务尚未提交就广播新配置或通知；失败任务可重试且不重做已成功副作用。
- 程序、核心、证书、防火墙都有明确的管理归属；不覆盖管理员自行维护的无关 nginx/systemd/sysctl 设置。

这些是将本机工具升级为持续管理平台的必要组成，属于后续设计，并非断言现有回环工具已经暴露公网漏洞。

## 12. 分阶段实施与完成标准

| 阶段 | 交付内容 | 必须满足的验收 |
| --- | --- | --- |
| A：明确边界并修复基础问题 | F1–F7 针对性修复；官方 API 与五协议能力验证；确认运行时路线 | 原场景可复现且修复后通过；服务停止态升级不变化；可选远端故障不拖垮有效本地输出 |
| B：统一业务与状态 | 类型化应用服务、单一配置真源、revision、任务/发布恢复；入口与账户关系拆分 | Web/CLI 同输入得到同业务结果；并发修改明确冲突；任何崩溃点可恢复到可解释状态 |
| C：建立完整管理面板 | 第 4 节日常功能整合，保留维护 CLI；管理员安全、证书与服务管理 | 按菜单映射逐项验收，无只能回旧菜单完成的日常操作；浏览器实际点击与移动端布局验证 |
| D：独立权益与真实限额 | 多用户凭据、到期、计量、账本、停用、周期重置、用户页 | 两用户同入口分别计量；到期/超额只影响目标；旧配置不能绕过停用；五协议与 TCP/UDP 分别验证 |
| E：性能和故障验收 | 有界后台任务、缓存、按需推送、Linux 长时测试 | CPU/RSS/FD/磁盘增长满足设定预算；管理器/核心重启、断网、满盘、慢客户端和恢复测试通过 |
| F：按需扩展 | 新协议/端点、多节点、邮件/Bot、IP/带宽策略 | 有明确需求和资源预算后增加；不影响单机基础运行 |

B、C、D 可在接口确定后交错开展，但不能在能力验证前对用户承诺所有协议都支持无扰动热更新或严格限额。

第一版统一平台的完成标准是：**原日常菜单能力有完整去向、共享后端与状态、独立账户可执行限制、已有 VPNGate 约束保持、故障恢复和资源边界可验证。** 不是只完成一个外观类似 s-ui 的前端，也不是要求立即实现参考项目全部集群功能。

### 12.1 重点验收场景

- 两个账户共享同入口但凭据不同，使用不同客户端格式，额度分别累计且不串号。
- 下载 URL 过期、账户使用到期、手动禁用、凭据轮换分别测试。
- 保持 QUIC/多路复用长会话，停用后尝试继续传输和新建流，验证真正终止；记录对其他用户的影响。
- 账户在同一时刻跨普通/VPNGate 多连接传输，不重复计费，也不各自获得完整剩余额度。
- 管理界面关闭、订阅监听关闭时，限额仍生效。
- 数据库暂时不可写、磁盘满、进程崩溃、未确认批次重放、周期边界和备份恢复不造成静默丢账或复活旧凭据。
- 必需来源故障只影响依赖它的输出；失效可选来源被剔除，不能继续发送过期节点。
- 自定义同前缀输出不被默认授权；跨账户请求、缓存和 304 不泄露其他账户产物。
- 无页面订阅时停止图表采样；计费不停止；慢网页不阻塞服务端处理。
- Linux 实测升级/回滚、停止态保留、端口冲突、证书失败、netns/防火墙所有权及 VPNGate 无泄漏路径。
- 在选定的账户数、连接数和资源预算下进行持续测试，验收结束检查资源能否回收。

## 13. 本轮结论

值得借鉴 s-ui 的完整资源管理与核心适配思路，也值得借鉴 2s-ui 的界面组织、按需实时数据、安全机制、维护任务和能力限制表达。本项目应将这些经验融入已有的 Go 管理底座、订阅编译器和 VPNGate 网关。

实施优先级应是：**修复已发现问题 → 核实运行时能力 → 统一模型与业务服务 → 整合完整 Web → 完成独立账户计量与停用 → 性能和故障验收 → 按需扩展。**

当前尚不能声称菜单已经完全整合、独立流量限制已经存在或项目已经达到生产稳定性。本报告给出了这些目标的具体缺口和验收方式，本轮没有落程序代码。
