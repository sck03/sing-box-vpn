# 性能、稳定性与资源边界

[架构](architecture.md) · [开发与验证](development.md) · [验收记录](unified-management-status.md)

## 当前优化

| 路径 | 实现与收益边界 |
| --- | --- |
| 账户列表 | SQL 分页/搜索/排序，只推进当前页账期；轻量 ID/名称选项不携带完整账本 |
| 账户导出 | 按账户/运行实例索引读取凭据；入口 ID 映射取代嵌套遍历，同次导出复用证书解析 |
| 用量结算 | 一轮变化池使用一个事务；计数快照采集后释放池锁再写 SQLite；累计检查点幂等 |
| 额度预留 | 保留 WAL/FULL 与先持久化后交付，64 KiB 预留上限不变；未以扩大误差换取吞吐 |
| 概览 | HTTP/SSE 共用短期缓存与一次在途采集，I/O 不持状态锁，失效版本防止旧快照重新入缓存 |
| 工作队列 | 空队列只读检查，避免争抢预留写锁；控制与只读探测分通道，自动任务去重 |
| 授权复查 | Tick 按活跃凭据集合批量查询，复用账户账期推进；入站绑定按 ID 建索引 |
| 前端 | 权益/授权服务端分页；本地表格排序、列显隐、密度偏好；更新保留焦点，维护页同步任务，隐藏页面断开 SSE |
| 备份恢复 | 发布锁内捕获数据库和证书；锁外 tar + age 流式加密到磁盘，避免 JSON/Base64 和整体明文副本；恢复仍有有界缓冲 |
| 订阅 | 共享能力筛选；未变化 sing-box 产物复用同核心校验；失败输出隔离，不拖垮启动恢复 |

以上是执行路径和调用次数的优化，不作为整机 CPU/RSS 或吞吐提升百分比。历史基准与长时间下载实验保存在[原优化日志](https://github.com/sck03/sing-box-vpn/blob/5975e773383b49dd6daca9f5406665eb47b06266/docs/optimization.md)，不能直接充当当前版本测量。

## 保留的边界

任务排队最多 32，单结果最多 256 KiB；已结束任务最多 200 条/30 天，详细结果总预算 8 MiB。下载授权上限只计算有效记录，失效记录保留 1,000 条/30 天。账期只清理最近 120 期以外且无未结清 lease 的记录。订阅单响应 8 MiB，生成 JSON 16 MiB；备份文件 96 MiB，数据库 80 MiB。节点探测最多 64 个、并发核心 2 个，每节点 12 秒。后台没有按账户创建常驻进程。

预留落盘仍产生数据库同步；批量授权查询和检查点不能消除预留同步成本。64 KiB 连续补充在 1 Gbit/s 流量下约需 1,900 次预留事务/秒，这是理论数量级而非实测吞吐。没有通过关闭 FULL 或扩大预留上界换取速度。连续崩溃的保守计费可以累积。订阅探测的账户材料在短锁内捕获，核心编译/校验在锁外执行；配置刷新和网络分发仍保持控制通道有序。

## 验证与清理

性能基准应与竞态/构建分开运行；前一轮首组 QEMU 对照曾受宿主测试活动影响，因此保留原始数据，不把所有时间变化归因于代码。本轮故障注入覆盖独立 tmpfs 满盘和 SIGKILL；不能代替真实断电、物理磁盘损坏及生产规模长时满载。当前验证与未覆盖项见验收记录。

## 前一轮 Linux 实测（当前重构未重新测量）

以下结果来自重构前提交 `78d8539` 所记录的验证，表中“本次”指当时的版本，不代表 schema 8 重构后的重新实测。当前重构的证据见验收记录，未据此声称整机 CPU、RSS 或吞吐提升。

环境：Ubuntu Linux amd64，QEMU TCG，2 vCPU / 2 GiB；SQLite WAL/FULL，虚拟磁盘。修复前版本 `461cb61` 和本次代码使用同一 `performance_test.go`。每项 3 次、每次目标 3 秒，以下是三次中位数；[原始记录](validation/2026-11-17-linux.json)保留单次值与资源信息。

| 项目 | 修复前 | 本次 |
| --- | ---: | ---: |
| 100 个活跃账户一轮授权 Tick | 1,123.38 ms | 115.77 ms |
| 每轮堆分配次数 | 10,598 | 2,804 |
| 每轮分配字节 | 503,688 | 259,163 |
| 64 KiB 持久预留计量吞吐 | 1.44 MB/s | 1.45 MB/s |
| SQLite 提交 P50 | 12.11 ms | 11.62 ms |
| SQLite 提交 P95 | 57.30 ms | 99.25 ms |
| 包含 20 ms 人工占锁的完整预留等待 | 62.27 ms | 91.25 ms |

批量授权减少了查询与分配；持久预留吞吐基本未变，提交尾延迟仍明显波动。当前单次提交 P95 最大约 439 ms，说明这台模拟器不能用来确定生产磁盘容量。没有因此降低 FULL 同步等级、扩大预留块或承诺代理带宽提升。

整个基准进程（含夹具与自动校准）修复前 CPU user/system 为 34.70/16.44 秒、峰值 RSS 15,616 KiB；本次为 37.86/18.92 秒、峰值 RSS 16,728 KiB。自动校准导致总迭代数不同，这组总 CPU/RSS 只描述进程开销，不用作等工作量节省比例。

停止宿主构建和测试后，另以 `-benchtime=30x -count=1` 固定相同工作量复测：

| 项目 | 修复前 | 本次 |
| --- | ---: | ---: |
| 100 个活跃账户授权 Tick | 654.60 ms | 96.74 ms |
| 每轮分配次数 | 10,594 | 2,805 |
| 64 KiB 持久预留吞吐 | 3.33 MB/s | 2.61 MB/s |
| 提交 P50 / P95 | 9.50 / 11.55 ms | 9.45 / 13.81 ms |
| 包含人工竞争的写入等待 | 95.09 ms | 70.81 ms |
| 整个基准进程 user + system CPU | 29.24 秒 | 10.18 秒 |
| 整个基准进程峰值 RSS | 15,616 KiB | 16,128 KiB |

两轮都确认授权批处理收益；固定样本中的预留吞吐反而下降，不能声称数据面吞吐提升。预留事务逻辑和同步策略未改动，虚拟磁盘时延仍是限制，生产部署应在实际磁盘上复测。CPU 数值包含各项夹具建立，RSS 没有下降。

面板持续负载：4 并发、每请求后间隔 50 ms，循环读取概览/权益/授权，持续 60.06 秒，完成 2,406 次请求，零错误；40.06 请求/秒，P50 29.82 ms、P95 80.85 ms。面板平均 CPU 为单核的 55.18%、峰值 RSS 23,284 KiB；空闲代理核心为 0.80%、29,592 KiB。没有进程丢失。此处是管理 API 负载，不含代理流量；复现脚本为 `scripts/measure-platform-linux.py`。

当前恢复内存预算：密文不超过 96 MiB，暂存磁盘后通过 Reader 解密；明文条目合计受 96 MiB 限制，scrypt 工作区约 64 MiB。移除了一份最大 96 MiB 的密文内存副本，主要明文与密钥派生缓冲约 160 MiB，另有文件页缓存、Go GC、SQLite、元数据和并发业务开销；不能据此承诺固定 RSS。单面板备份/恢复互斥，输入输出临时文件均在错误和取消后清理。

临时测试放 `.test/`、工具放 `.tools/`、当前发行包放 `.build/release/`。删除确认无用的旧材料；执行环境不能删除的材料统一移入仓库根目录 `待手动删除/`，该目录被 Git 忽略且不进入发行包。保留开发工具、必要缓存与虚拟机的基础磁盘依赖。旧设计文档仅在 Git 历史中保留，避免与现行部署说明混淆。
